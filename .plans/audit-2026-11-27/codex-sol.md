## 3. Detailed findings

### A01 · Gate the actual packed OpenTUI import and first TTY frame

**Trigger and impact.** Published `bun add -g @kitsunekode/sweep` can resolve an unrelated OpenTUI in a shared Bun global tree. The published artifact's optional peer range is also beneath the UI's required API. Paired installs reproduced the missing export on the public artifact and succeeded with the current local tarball. This gives high confidence in the direct dependency fix on the tested Bun version. It does not establish behavior across supported Bun versions, global install order, or platforms.

`scripts/bundle.ts:59–68` bundles the React adapter while leaving core external. `apps/cli/src/handlers/shared.ts:301–345` checks resolution only and throws a missing-package error only when no resolver succeeds. A resolved old package still passes. `apps/cli/src/handlers/ui.ts:123–130,202–206` then imports the bundle, where the real compatibility failure happens. `preflight.ts:131–196` checks manifest and outputs, and `scripts/publish-release.ts:177–190` checks the packed manifest's publishable shape. Neither compares the built UI's external imports with the tarball's runtime dependency contracts. The npm smoke explicitly excludes the terminal. `docs/users/getting-started.md:26–29` already describes the corrected source as though it were in the latest release.

**Fix.** Keep core a direct dependency first. Generate the release check from bundler externals or metadata, inspect the packed manifest, and load the actual packed UI from an isolated Bun global install beside both older core and a tool that depends on it. Drive first frame and clean exit in a PTY, and test a clear diagnostic for missing native assets and incompatible exports. Validate the actual sibling import and report its resolved version/path and platform when possible. Pin the qualified core version, or test the allowed minor/patch range and lower bound. A semver range cannot prove a named export exists.

Vendoring is a separate distribution decision. Prefer the direct dependency plus artifact-level gate unless the conflict recurs under a supported package manager. A vendor proof would need platform-native lookup, musl, optional packages, licenses, duplicated package cost, and JS adapter/core identity checks. The existing standalone build already supplies a tested model for embedding native assets.

### A02 · Treat idle time as a bounded estimate and keep uncertain projects out of idle queues

**Trigger and impact.** A project had a 120-day-old manifest and source-directory mtime, an existing `src/app.ts` edited immediately before status, and one safe artifact. Both engines showed one idle project at the 30-day threshold. Updating a file's contents does not update the containing directory mtime. The index reads top-level mtimes and Git metadata, so a recent unstaged edit in an existing nested file can remain unseen. The “what nobody has touched” promise affects `--idle` selection and the Projects idle shortcut, although the deletion scope remains artifact-only. The existing activity test ages the `src` directory itself and therefore does not exercise this case.

Evidence at `packages/core/src/project-activity.ts:200–235`, `project-activity.test.ts:23–35`, `planner.ts:125–134`, `packages/ui/src/app.tsx:1594–1613` and `docs/users/commands.md:79–86`. Git index or reflog changes can also move the signal in the other direction without an edit. A recent Git signal remains useful as a conservative activity hint.

**Fix.** Introduce an activity-confidence state with a bounded recent-source check and an explicit unknown result when coverage cannot support idle. Qualify ordinary existing-file edits, semantic Git changes, generated output, size fallbacks and cancellation. Share the conservative decision across CLI and TUI and describe it as observed activity.

### A03 · Preserve scan coverage and distinguish a guarded tree from an empty one

**Trigger and impact.** With one unreadable child and no visible artifacts, `scan --json` reported one skipped directory but `status` printed “Nothing to free here” and returned success under both engines. A tree containing only opt-in dangerous output produced the same text, although `protectedCount` exists in JSON. Partially sized candidates similarly contribute lower-bound estimates without a coverage field in `StatusSummary`. An automation widget cannot tell complete zero from incomplete zero or a lower-bound total. For sub-day `--idle` values the reported rounded `days` can also disagree with the actual threshold.

Evidence at `apps/cli/src/handlers/status.ts:36–46`, `packages/core/src/status.ts:33–41,86–109`, `packages/protocol/src/index.ts:365–390` and `packages/display/src/index.ts:423–440`. The full scan handler preserves coverage and already offers a model for status.

**Fix.** Carry additive scan and byte-coverage fields plus an exact idle duration in the JSON. Render skipped, guarded-only, empty, and lower-bound outcomes distinctly. Document and test the automation exit contract. Keep status read-only.

### A04 · Keep missing upstream separate from merged ancestry

**Trigger and impact.** Created a linked worktree whose branch was ahead of and outside `main`, tracked a local remote ref, and removed that stale tracking ref. Git's ancestry check stayed false. Sweep reported `upstream_gone`. The grouping code puts that state under “Finished worktrees” when the activity threshold is met. A branch can be deleted without landing its work. A stale or unavailable remote can make the same label ambiguous. W1 currently adds triage metadata, while the future W3 plan proposes worktree-removal authority. This is a release issue in the current presentation and a prerequisite for W3.

Evidence at `packages/core/src/worktree-info.ts:104–110,134–164`, `packages/ui/src/projects.ts:22–32,141–150` and `.plans/clove-inspired-ux.md` W1/W3. The fixture retained the artifact's existing risk class.

**Fix.** Reserve “Finished” for proven ancestry against a verified base. Show a gone upstream as “Tracking branch missing · verify Git status” with an unknown completion state. Add unmerged-but-gone, missing base and normal merged fixture cases. Keep the missing-upstream signal out of any later removal eligibility rule.

### A05 · Qualify a Linux ABI floor and expose fallback causes

**Trigger and impact.** The published x64 engine requires GLIBC_2.39. The GNU target built on the current Ubuntu runner can produce binaries outside the promise older Ubuntu, Debian and RHEL users reasonably infer. `isRustEngineAvailable` stores only a boolean and the JS directory worker under Bun starts `node`. A no-Node, no-engine probe returned an exit-2 budget wrapper around a missing runtime. It advised scanning a smaller tree even though the blocker was a missing runtime. G4 covers probe lifecycle. This finding adds release floor and runtime-capability acceptance criteria to G8.

Evidence at `.github/workflows/native-engine-release.yml:35–43,74–87`, `packages/core/src/rust-engine.ts:708–744`, `directory-reader.ts:73–85` and `docs/users/platforms.md:26–36`. An apt-installed Node would change the fallback outcome, so Node-installed users may only notice performance differences.

**Fix.** Publish an explicit Linux support floor, build against it, inspect ELF requirements, and run the actual npm/standalone artifacts in the oldest supported images and without Node. Return a structured reason for an unavailable/incompatible native engine and distinguish runtime capability from scan-budget exhaustion. Keep standalone native-backed operation verifiable and make the portable reader able to run with the runtime it advertises.

### A06 · Make init's create/replace operation enforce its file policy

**Classification.** Private security advisory, not a public issue. The audit did not exercise a malicious file or race.

**Impact.** `packages/core/src/config.ts:250–272` checks the path, then uses a separate unrestricted write. The API's “refuses to write through a symlink” expectation and no-overwrite behavior rely on the prior observation remaining true through the actual open. The TUI writer has a better defined exclusive-create and staged replacement contract at `config.ts:298–310` and its tests. The ordinary mode defect is separate evidence of the same code path's weak creation semantics. Under umask 002 init produced 0664 and auto-loading then refused it.

**Fix.** Make create exclusive with an explicit safe mode and use a staged, trusted replacement flow for a reviewed force write. Consolidate writer primitives with the TUI path while preserving init's replacement semantics. Test ordinary existing-file refusal, permissions under 002, failure before commit and policy enforcement at the final write.

### A07 · Keep the previous install until the replacement proves it runs

**Trigger and impact.** The shell installer stages and verifies integrity, then renames over the live destination. Its execution check happens after this rename. On a non-runnable binary the else branch prints a note and the last command exits successfully. This means a supported upgrade can destroy the user's working command or a bootstrap script can register success on an incompatible host.

Evidence at `install.sh:46–72,74–84`. Checksum verification and same-filesystem rename are good baseline controls. An executable can still be incompatible with the host.

**Fix.** Create the stage securely and exclusively in the destination filesystem, probe the staged binary, and install only after success. Fail nonzero with detection details while preserving any existing executable. Extend G8 with a staged-probe failure fixture and asset-format/retry coverage.

### A08 · Restore focus in the landing review demo and model deliberate confirmation

At 1280 px the review button was focused, then activated. The next focused element was the final “Confirm” button. Clicking Back returned to choose mode with focus on `BODY`. A keyboard user pressing Enter twice can produce the demo's simulated receipt without reading the review. The demo's plain-key shortcuts are scoped to the demo, so falling back to `BODY` also breaks its shortcut flow. The TUI has a distinct confirmation key and preserves context on cancel. The web simulation should teach that behavior.

Evidence at `apps/docs/src/components/landing/queue-demo.tsx:74–108,186–225` and `.docs/ux-principles.md:26–39`.

**Fix.** Focus the review heading or a Back control on entry, restore focus to the triggering control on cancel, and name the final action for the chosen mode, such as “Simulate moving to trash”. Add a keyboard-only browser smoke that covers first focus, review, cancel, receipt and reset. Use stable focus refs instead of DOM query selection if available.

### A09 · Keep sample paths and rule scope legible on narrow screens

At 320 px the document fit the viewport. The idle report's path column was 37 px wide and all four sample paths clipped. The longest had 203 px intrinsic width. Paths had no visible expansion control. The queue demo clipped several paths, including a 203 px path in 114 px. Its visible detail region shows the reason but no complete path. CSS sets `display:none` for the rules table's “Applies to” column at 760 px, so users lose a distinction between apply and scan. The review component already uses `overflow-wrap:anywhere` for paths.

Evidence at `landing.css:589–608,767–779,869–886,2070–2091`, `landing.tsx:308–319,468–489` and `queue-demo.tsx:154–165`. The mobile loss happened in both sampled theme classes.

**Fix.** Switch to two-line mobile sample rows with a full wrapping path and right-aligned numeric detail. Put scope under each rule at narrow widths and leave the column visible at larger widths. Let focus or row activation reveal the full demo path and reason. Browser-test 320 px, 200% zoom and keyboard access.

### A10 · Use one scope and meaning for cleanup estimates across review views

At the same settled fixture, Projects read “6.0 MiB you can reclaim” plus “78.1 KiB guarded”; Folders read “6.1 MiB reclaimable” and included the 78 KiB dangerous tier. The displayed sizes match their independent sums. Folders includes dangerous estimates in `buildLedger`; Projects and `status` sum safe and caution. Projects also omits `selectedBytesPartial` from the queued answer, although Folders and confirmation show the qualifier. A single summary should hold under view changes, scope filters and partial sizing.

Evidence at `packages/ui/src/LedgerBand.tsx:31–41,175–191,219–255`, `ProjectsView.tsx:313–354`, `app.tsx:2858–2874` and `packages/core/src/status.ts:33–41`. At 80 and 100 columns Folders drops risk words from the legend. The symbols still offer a compact treatment, but the text that makes them interpretable is less available.

**Fix.** Use shared named quantities for eligible estimates, guarded estimates, blocked, queued and visible scope counts. Describe the denominator consistently when filters are active. Preserve partial-value markers in every queued summary, then derive both themes and renderers from the same data.

### A11 · Make the binary release handoff restartable after npm success

The publish script skips versions already present in npm, and the binary dispatch runs only when Changesets reports a publication. If a network or permission fault interrupts after npm publication and before the `v` tag push or dispatch, an ordinary rerun can do no binary work. Manual binary dispatch is documented and supported, but the path assumes the tag already exists. A retry should reconcile the exact qualified tag and required assets across both npm and GitHub.

Evidence at `scripts/publish-release.ts:170–205`, `.github/workflows/release.yml:175–196`, `.github/workflows/cli-binaries.yml:125–153` and `.docs/release.md:131–135`. Explicit dispatch is correct for actions triggered with the workflow token.
